Falcon Web — Developer Tutorial

A full walkthrough of this project: what it is, why each tool was chosen, how it was built step by step, and the real mistakes made (and fixed) along the way.

Who this is for

This guide is written for a junior developer who is comfortable with basic JavaScript and HTML/CSS, but new to Next.js, authentication, Docker, and the App Router. It doesn't just say what to do — it explains why, so the reasoning transfers to other projects, not just this one. Read it alongside the actual code in this repo; every section names the real file it's talking about.

What this project is

Falcon Web is an MVP (minimum viable product) template for small-business websites: a public marketing home page, an admin login, and a protected admin dashboard. It's meant to be copied and customized for real client projects rather than used as-is — see Section 12 for how that works.

2. Prerequisites

Install these before touching the code. Each one is explained, not just listed.

Node.js (v20+)

The JavaScript runtime that runs Next.js, npm, and all build tooling. Next.js 16 specifically requires a recent Node version — older versions will fail to install dependencies or build.

npm (comes with Node.js)

The package manager used to install and manage this project's dependencies (package.json). Alternatives exist (yarn, pnpm) but this project standardizes on npm — package-lock.json is committed, so stick with npm to keep dependency versions consistent across machines.

Docker Desktop

Runs PostgreSQL locally in an isolated container, so your dev database doesn't depend on installing Postgres directly on your machine (which can conflict with other projects — see Section 8). Docker also means "it works on my machine" is more likely to mean "it works on everyone's machine," since the database version and config are defined in code (docker-compose.yml), not installed by hand.

Git

Version control. If you don't already have a solid mental model of commits, branches, and .gitignore, learn that before this project — it's assumed knowledge here.

A code editor (VS Code recommended)

Any editor works, but VS Code has the best Next.js/Tailwind/ESLint integration out of the box (autocomplete for Tailwind class names, inline ESLint errors).

3. The stack, and why each piece was chosen

Nothing here was picked at random. Each choice trades something for something — knowing the trade-off is more valuable than memorizing the choice.

Next.js (App Router)

What it is: a React framework that adds file-based routing, server rendering, API routes, and build optimization on top of React.

Why chosen: a plain React app (e.g. via Vite) gives you a client-only single-page app — every page ships as JavaScript that runs in the browser, which is slower for first load and bad for SEO (search engines have to execute JS to see content). Next.js renders pages on the server by default, sending real HTML on first load, then "hydrates" into an interactive React app. For a marketing site where a client cares about Google ranking and fast load times, that matters directly.

Why App Router specifically (not the older Pages Router): App Router uses React Server Components by default, has built-in support for layouts, loading states, and colocated API routes, and is what Vercel (the deployment target) actively develops for. The Pages Router still works but is in maintenance mode.

React

The UI library Next.js is built on. Components, props, hooks (useState, useEffect) — if you don't know these yet, learn plain React before trying to understand Next.js specifics, since Next.js assumes you already have this foundation.

PostgreSQL

What it is: a relational (SQL) database.

Why chosen over, say, MongoDB or SQLite: the data here (an admins table, eventually products/content tables) is structured and relational — rows with fixed columns, unique constraints (one email per admin). SQL databases enforce that structure at the database level, not just in application code, which catches bugs earlier. Postgres specifically was chosen because Vercel Postgres — the production database — is Postgres, so local dev and production use the same database engine, avoiding "works locally, breaks in prod" bugs caused by subtle differences between database systems.

Why raw SQL instead of an ORM (like Prisma): this project talks to Postgres directly via the pg npm package (see lib/db.js) rather than through an ORM. For a small schema (one table so far), raw SQL is more transparent — you see exactly what query runs — and avoids the learning curve and build-step overhead of an ORM. As the schema grows, introducing an ORM later is a reasonable evolution, not a mistake to avoid now.

Auth.js (NextAuth), Credentials provider, JWT sessions

What it is: a battle-tested authentication library for Next.js. "Credentials provider" means email + password login (as opposed to "OAuth provider" which would mean "Sign in with Google," etc.).

Why not roll your own auth: authentication is deceptively easy to get wrong — session fixation, CSRF, insecure cookie flags, timing attacks on password comparison. Auth.js handles all of that correctly by default. Writing your own login system from scratch is a common junior-developer mistake; don't.

Why JWT sessions instead of database sessions: Auth.js supports two session strategies. Database sessions store a session record in Postgres and look it up on every request. JWT sessions encode the session data into a signed, encrypted token stored in a cookie — no database lookup needed to verify a session. For a single-admin app with no need to remotely revoke sessions instantly, JWT is simpler and faster. The trade-off: you can't force-invalidate a JWT session early (e.g. "log this user out right now, everywhere") without extra work — acceptable here, but worth knowing.

bcrypt

What it is: a password-hashing library.

Why it matters: passwords are never stored in plain text — ever, in any app. bcrypt takes a password and a random "salt," and produces a one-way hash: easy to verify a password is correct, effectively impossible to reverse back to the original password. If the database ever leaks, attackers get hashes, not passwords. bcrypt is deliberately slow (tunable via its "cost factor," set to 10 here in scripts/seed.js) — that slowness is a feature, since it makes brute-forcing every possible password far more expensive for an attacker.

Tailwind CSS v4

What it is: a utility-first CSS framework — instead of writing custom CSS classes like .hero-button, you compose small utility classes directly in JSX: className="rounded-full bg-primary px-6 py-3".

Why chosen: it avoids the classic CSS problem of naming things and managing a growing, hard-to-track stylesheet. Styles live next to the markup they affect, so there's no hunting through a separate CSS file to find what's applied where. It also has excellent dark-mode support and, combined with a small config, makes theming (see Section 9) straightforward.

Why v4 specifically: Tailwind v4 moved configuration into CSS itself (@theme blocks in app/globals.css) instead of a separate tailwind.config.js file. This project has no tailwind.config.js at all — that's not missing, it's the new normal for v4. It's also noticeably faster to build.

Docker & docker-compose

Already covered under Prerequisites — the short version: reproducible local Postgres, defined in code (docker-compose.yml), matching the production database engine.

Vercel (deployment target)

Next.js's own creators run Vercel, so deployment there is close to zero-config — push to GitHub, connect the repo, done. It also offers Vercel Postgres, which is why Postgres was chosen for local dev too (see above). Other hosts work with Next.js, but Vercel has the least friction for this exact stack.

5. Core concepts to actually understand

Don't just copy patterns from this repo — understand why they exist, so you can apply the same reasoning elsewhere.

Server Components vs. Client Components

In the App Router, every component is a Server Component by default — it runs on the server, never ships its JavaScript to the browser, and can't use hooks like useState or browser-only APIs. A component becomes a Client Component only when it starts with "use client" at the top of the file — that's how the app opts into interactivity for things like the mobile nav menu (components/SiteHeader.js) or the login form (app/admin/login/page.js), which need state and event handlers.

Why it matters: Server Components mean less JavaScript shipped to the browser (faster pages) and let you query the database directly inside a component (see app/admin/(protected)/page.js, which calls getServerSession directly — no API call needed). Default to Server Components; only add "use client" when you actually need interactivity or browser APIs.

Route groups: (protected)

A folder wrapped in parentheses, like app/admin/(protected)/, is invisible in the URL — app/admin/(protected)/page.js is still just /admin. The reason to use one here: a layout.js file applies to every page nested inside its folder. We want the admin nav bar and sign-out button to show on the dashboard but not on the login page, even though both live under /admin. Route groups let you scope a layout to only part of a route tree.

Access control via proxy.js

proxy.js (the file was called middleware.js before Next.js 16 renamed the convention — same idea) runs on the server before any page renders, for every matching request. This project uses it to enforce three rules in one central place instead of scattering auth checks across every page:

  1. / and /admin/login are always allowed through.
  2. /admin requires a valid session — checked via getToken() from next-auth/jwt, which reads and verifies the signed JWT cookie without needing a database round-trip. No valid token → redirect to /admin/login.
  3. Anything else → rewritten to the 401 "Site Unavailable" page.

A real bug we hit here: the first version of this logic didn't explicitly allow /api/auth/* through, so Auth.js's own login/CSRF endpoints got caught by the "anything else → 401" rule and login broke entirely. Fixed by adding an explicit allowlist. See Section 8 for the full story — it's a good example of why testing the actual auth flow end-to-end (not just "the page loads") matters.

Config-driven content (config/site.js)

Every piece of page copy — headings, product names, social links, the admin login text — lives in one plain JS object in config/site.js, and components read from it rather than hardcoding text inline. Optional sections (like the "Trusted By" logo strip) render only if their key isn't null: {trustedBy && (<section>...</section>)}.

Why: this is what makes the template reusable. Customizing a copied project for a new client is "edit one file," not "hunt through ten component files for hardcoded strings." It also means deleting a section is "set a key to null," not "carefully delete JSX without breaking the layout."

Environment variables

DATABASE_URL, NEXTAUTH_SECRET, and NEXTAUTH_URL live in .env.local, which is gitignored — never committed, because it holds real secrets. .env.example and .env.local.example are committed and document which variables exist and their shape, without real values, so a new developer knows what to create. Next.js loads .env.local automatically for the dev server and build, but a standalone script like scripts/seed.js doesn't get that for free — that's why its npm script explicitly passes --env-file=.env.local.

6. React, Next.js & SQL — the 20% that gets you 80% there

This is the fast-track version of each technology — not the full docs, just the core mental model you need to read and modify this codebase confidently. Everything past this section assumes you understand what's here. Explore the official docs for the rest, later, once you actually need it — don't front-load advanced material you have no concrete use for yet.

React, in six ideas

1. JSX is just JavaScript wearing an HTML costume

<h1>{hero.heading}</h1> looks like HTML but compiles to plain JavaScript function calls. Anything inside curly braces {...} is a real JavaScript expression — a variable, a function call, a ternary. That's why you'll see things like {new Date().getFullYear()} in the footer (app/page.js) — it's just JS running inline.

2. A component is a function that returns JSX

That's it. export default function Home() { return (<div>...</div>); } in app/page.js is a component. It can accept props — arguments passed in from whoever renders it — like AdminLayout({ children }) in app/admin/(protected)/layout.js, where children is whatever page got nested inside that layout.

3. State is memory that triggers a re-render when it changes

useState is how a component remembers something between renders — like whether the mobile menu is open. From components/SiteHeader.js: 

const [menuOpen, setMenuOpen] = useState(false);

// later, in the JSX:
<button onClick={() => setMenuOpen((open) => !open)}>

// and:
{menuOpen && (<div>...mobile menu...</div>)}

Calling setMenuOpen(...) doesn't just change a variable — it tells React "re-run this component's render," so the new value shows up on screen. This is the single most important idea in React: you never manually update the DOM; you update state, and React figures out what needs to change.

4. Conditional rendering is just JavaScript && and ternaries

There's no special "if" syntax in JSX — you use normal JS operators. This whole template's "optional sections" feature (Section 5) is built entirely on this one pattern, used throughout app/page.js: 

{stats && (
  <section>...stats content...</section>
)}

If stats is null, the whole expression short-circuits to null, and React renders nothing. If it's an object, React renders the JSX after the &&.

5. Lists need .map() and a key

To render a list of things, you .map() over an array and return JSX for each item — same as products.items.map((product) => ...) in app/page.js. Every item needs a unique key prop (usually an id) so React can track which item is which across re-renders, instead of accidentally mixing them up.

6. Controlled form inputs

An input whose value comes from state, and updates state on every keystroke, is called "controlled." From app/admin/login/page.js: 

const [email, setEmail] = useState("");

<input
  value={email}
  onChange={(e) => setEmail(e.target.value)}
/>

This is why the value shown in the box always matches what's in state — React is the single source of truth for the input, not the browser's own DOM.

Next.js App Router, in five ideas

1. Folders are URLs, page.js is the page

app/admin/login/page.js renders at /admin/login. There's no separate router config file to maintain — the file tree is the route table. A folder with no page.js inside it (like app/admin/(protected)/) contributes no URL segment of its own.

2. layout.js wraps everything nested inside it

app/layout.js wraps the entire site (fonts, the session provider, the theme script). app/admin/(protected)/layout.js wraps only the dashboard, adding the admin nav bar and sign-out button — without affecting /admin/login, which sits outside that route group. Layouts nest: a page is rendered inside every layout above it in the folder tree.

3. Server Components can be async and query data directly

Because a Server Component runs on the server, it can await a database call right inside the component — no separate API endpoint, no client-side fetch, no loading spinner needed. From app/admin/(protected)/page.js: 

export default async function AdminPage() {
  const session = await getServerSession(authOptions);
  return <div>{session?.user?.email}</div>;
}

This only works in Server Components. A Client Component (anything marked "use client") can't be async like this — it has to fetch data through useEffect or a library, because it runs in the browser, where you can't just "await the database."

4. "use client" is an opt-in, not the default

Add it to the very top of a file the moment you need useState, useEffect, event handlers like onClick, or any browser-only API. Everything else stays a Server Component by default — which is what you want, since it ships less JavaScript to the browser. If you forget it and try to use useState in a Server Component, Next.js will throw a build error telling you exactly that.

5. A route handler is an API endpoint, not a page

A file named route.js instead of page.js — like app/api/auth/[...nextauth]/route.js — doesn't render a page. It exports functions named after HTTP methods (GET, POST) that return a Response. That's how this project's login/session endpoints work. [...nextauth] is a "catch-all" dynamic segment — it matches /api/auth/anything/here, letting Auth.js handle multiple sub-routes (signin, callback, session, csrf) from one file.

SQL & Postgres, in five ideas

1. A table is rows of the same shape

From db/schema.sql: 

CREATE TABLE IF NOT EXISTS admins (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Every row in admins has exactly these four columns. SERIAL PRIMARY KEY auto-generates a unique, ever-increasing id per row. UNIQUE on email means the database itself refuses a second row with the same email — you get that guarantee for free, without writing application code to check for duplicates. NOT NULL means the database will reject an attempt to insert a row missing that value.

2. The four verbs: SELECT, INSERT, UPDATE, DELETE

SELECT id, email FROM admins WHERE email = 'a@b.com';
INSERT INTO admins (email, password_hash) VALUES ('a@b.com', '$2b$10$...');
UPDATE admins SET password_hash = '$2b$10$...' WHERE email = 'a@b.com';
DELETE FROM admins WHERE id = 4;

WHERE filters which rows a statement applies to — leave it off an UPDATE or DELETE by accident and you'll modify every row in the table. Always double-check your WHERE clause before running a destructive query, especially by hand against a real database.

3. Parameterized queries — the single most important habit

Never build a query by concatenating a string together with user input. From app/api/auth/[...nextauth]/route.js: 

// Correct — the value is passed separately, never inserted into the SQL text:
await db.query(
  "SELECT id, email, password_hash FROM admins WHERE email = $1",
  [credentials.email]
);

// NEVER do this:
await db.query(
  `SELECT * FROM admins WHERE email = '${credentials.email}'`
);

The second version is a SQL injection vulnerability — a malicious value for email like ' OR '1'='1 could rewrite the meaning of the query entirely, potentially returning every row in the table or worse. The $1 placeholder tells Postgres "this is a value, never treat it as SQL syntax," no matter what it contains. This one habit prevents an entire, very common class of security bugs — use it for every single query that includes any value that didn't come from your own code.

4. Connections are expensive — reuse a pool

Opening a database connection has real overhead (a TCP handshake, authentication). lib/db.js creates one shared Pool from the pg package instead of opening a new connection per request, and every query borrows a connection from that pool and returns it when done. In development, it's also cached on globalThis so Next.js's hot-reload doesn't accidentally spin up a new pool (and leak connections) on every file save.

5. You'll need JOINs once you have more than one table

This project only has one table so far, so there's no join to show yet — but the moment you add a second related table (say, a products table with an admin's id as a foreign key), you'll need JOIN ... ON to combine rows from both tables in one query. Worth learning when you actually hit that need, not before.

7. Build steps, in the order they actually happened

This mirrors PLAN.md. Follow this order if you're building something similar from scratch — each step depends on the previous one being in place.

  1. 1. Scaffold Next.js

    npx create-next-app@latest . --app --js --tailwind --eslint --no-src-dir --import-alias "@/*" --use-npm

    --app selects the App Router. --no-src-dir keeps app/ at the repo root instead of inside src/ — a style choice, both work. --import-alias "@/*" lets every file import with @/lib/db instead of relative paths like ../../lib/db.

  2. 2. Install extra dependencies

    npm install next-auth pg bcrypt @tabler/icons-react

  3. 3. Docker Postgres for local dev

    Write docker-compose.yml, then docker-compose up -d to start it in the background.

  4. 4. Env files

    Create .env.example, .env.local.example, and your real .env.local (generate NEXTAUTH_SECRET with openssl rand -base64 32 — never reuse a secret across environments).

  5. 5. Database schema + seed script

    Write db/schema.sql and scripts/seed.js, then npm run seed to create the admins table and insert the first bcrypt-hashed admin.

  6. 6. Auth.js setup

    app/api/auth/[...nextauth]/route.js — a Credentials provider whose authorize() function looks up the email in Postgres and compares the password with bcrypt.compare(). JWT session strategy. Wrap the app in <SessionProvider> (via a small client-component wrapper, since SessionProvider itself needs "use client" and app/layout.js is a Server Component).

  7. 7. Build the pages

    Home, admin login, admin dashboard (behind the (protected) route group), Site Unavailable — all reading from config/site.js.

  8. 8. Central access control

    proxy.js, as described in Section 5.

  9. 9. Styling & theming

    Tailwind v4, dark mode via a .dark class toggle, and the master color token system — see Section 9.

  10. 10. README

    Document the setup steps for the next developer (or your future self).

  11. 11. Sanity check

    Actually test every route and the full login flow before calling it done — see Section 10.

8. Real pitfalls we hit (and how they were diagnosed)

These aren't hypothetical "watch out for" warnings — every one of these actually happened while building this exact project. Reading how they were diagnosed is often more useful than the fix itself.

"create-next-app" refused to scaffold into the project folder

Symptom: it listed CLAUDE.md, PLAN.md, mockup/ as "conflicting files" and exited.

Cause: the tool only tolerates a specific allowlist of pre-existing files (like .git, README.md) in a non-empty target directory.

Fix: scaffold into a temporary sibling folder, then move everything except its own .git into the real project folder, preserving the original git history.

npm install ran in the wrong directory

Symptom: dependencies "installed successfully" but never showed up in package.json.

Cause: the terminal's working directory was one level up (the parent folder containing multiple unrelated projects), not inside falcon-web — easy to miss if you're not checking the prompt path.

Lesson: always check where a command actually ran before debugging why it "didn't work" — a stray package.json and node_modules appeared in the parent directory and had to be cleaned up.

Postgres port conflict (5432 already in use)

Symptom: the seed script failed with password authentication failed for user "falcon", even though the Docker container's credentials were verifiably correct when tested from inside the container.

Diagnosis: netstat showed two processes bound to port 5432 — Docker's backend, and a pre-existing native Windows Postgres service. Connections from the host were landing on the wrong one.

Fix: remap the Docker container to a different host port (5433) rather than touching a Postgres service that might belong to another project.

Lesson: "wrong password" errors aren't always about the password — always verify you're actually talking to the service you think you are, e.g. by testing the connection from inside the container first to rule out a routing problem.

The proxy blocked NextAuth's own API routes

Symptom: login silently failed — CSRF token requests and login POSTs both returned 401.

Cause: the "anything not public or protected → 401" catch-all rule in proxy.js didn't know about /api/auth/*, so Auth.js's own internal endpoints got treated as unrecognized routes.

Fix: add an explicit always-allowed prefix for /api/auth.

Lesson: when you write a catch-all "deny by default" rule, you must explicitly enumerate every legitimate exception — it's easy to forget a framework's own internal routes.

Protected-prefix matching hid a routing bug

Symptom: visiting /admin/some-page-that-does-not-exist returned Next.js's generic 404 instead of the custom "Site Unavailable" page.

Cause: the proxy treated any path starting with /admin as "protected," so it passed through to Next's router — which then correctly reported 404 for a page that doesn't exist, but that's not the behavior the brief called for.

Fix: changed to an explicit allowlist of real admin routes instead of a prefix match, so an unbuilt /admin/* path correctly falls through to the "unrecognized route" branch.

Tailwind v4 CSS variable self-reference

Symptom: caught before shipping — the master theme's @theme inline block used the exact same variable name (--color-primary) as the :root/.dark token it was supposed to point to.

Why that's broken: a CSS custom property can't validly resolve by referencing itself — the browser has no way to know which value you meant.

Fix: give the raw tokens plain names (--primary) and only prefix with --color- inside the @theme inline mapping that exposes them as Tailwind utilities — the same pattern the scaffold already used for --background → --color-background.

9. The theming system

app/globals.css defines a small set of named color tokens — primary, primary-hover, primary-foreground, accent, surface, surface-alt, border-color, text-muted. Tailwind's @theme inline block exposes these as real utility classes: bg-primary, text-primary-foreground, border-border, and so on. Every component uses these tokens instead of hardcoded colors like bg-gray-900.

Six color themes, each with a light and dark variant: Ocean Blue, Forest Green, Desert Orange, Royal Purple, Ferrari Red, and Golden. Each theme's 8 token values live under a [data-theme="..."] / [data-theme="..."].dark CSS selector pair in globals.css — "Ocean" is the default and lives on plain :root / .dark so the page still has color before any script runs. Color theme and light/dark mode are two independent axes: which color theme is active is controlled by a data-theme attribute on <html>; whether it's light or dark is controlled by the .dark class on the same element. The CSS selectors combine both, e.g. [data-theme="forest"].dark only matches when both are set.

components/ColorThemeSwitcher.js is the dropdown that sets data-theme and persists the choice to localStorage under falcon-color-theme, mirroring how components/ThemeToggle.js toggles .dark and persists to falcon-theme. Both controls are wired in next to each other everywhere the header appears: the home page, admin layout, login, blog, and the error/401 pages.

Why this matters: recoloring the entire site for a new client is a one-file edit (change the hex values in globals.css) instead of hunting through every component for hardcoded colors. docs/theme-prompt-template.md is a ready-made prompt for exactly that task — the same pattern used to derive all six shipped themes.

Dark mode and the flash-of-wrong-theme problem: Tailwind v4 needs an explicit @custom-variant dark (&:where(.dark, .dark *)); to make dark: classes respond to a .dark class on <html>, rather than only the OS-level prefers-color-scheme. A small inline script in app/layout.js (components/ThemeScript.js) sets both the .dark class and the data-theme attribute synchronously, before the page paints, based on localStorage or system preference — without it, you'd see a flash of the wrong theme (and wrong color) on every page load.

Pitfall hit here: setting data-theme on <html> from that inline script — which runs before React hydrates — made React log a hydration-mismatch warning, since the server-rendered HTML never had that attribute. The fix is suppressHydrationWarning on the <html> tag in app/layout.js, the standard escape hatch for exactly this pattern (documented in Next.js's own dark-mode guidance).

10. Testing & verification

"The page loads" is not the same as "it works." Every feature in this project was verified against its actual specified behavior, not just checked for the absence of an error.

  • npm run build — catches type errors, broken imports, and misconfigured metadata before they reach production.
  • curl-based route checks — for every route, assert the actual HTTP status code matches the spec: 
    curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/random-page   # expect 401
  • Full login flow tested end-to-end with a real CSRF token and cookie jar, not just "the login page renders" — fetch a CSRF token, POST credentials, confirm a session cookie is issued, then confirm the protected page returns 200 with that cookie and 307 without it.
  • A manual browser click-through (dark mode toggle, mobile nav, full login → dashboard → sign-out) to catch anything a curl script can't — actual rendering, layout, interaction.

11. Security notes

  • Passwords are bcrypt-hashed, never stored or logged in plain text.
  • Secrets never committed — .env.local is gitignored; only .env.example (no real values) is tracked.
  • Sessions are signed JWTs verified server-side on every protected request via NEXTAUTH_SECRET — a different secret must be generated for every environment (never reuse the local one in production).
  • Known gap, intentionally left for later: there's no rate limiting or lockout on /admin/login — right now it's an unlimited brute-force target. Acceptable for an internal MVP demo, not for a real production login with a single admin account guarding real business data.
  • Known gap: no password-reset flow — the only way to change the admin password today is re-running the seed script.

12. Starting a real project from this template

  1. Copy this repo to a new folder (avoid dots in the name — Vercel project names can't contain them).
  2. Send docs/project-profile-intake-form.docx to the client and get it filled in.
  3. Feed the completed form to Claude Code to populate config/site.js.
  4. Use docs/theme-prompt-template.md, filled in with the client's brand color, to recolor app/globals.css.
  5. Set up a fresh .env.local, a new NEXTAUTH_SECRET, and re-run npm run seed with the client's real admin credentials.
  6. Follow the Vercel deployment steps in README.md.

13. Glossary

SSR (Server-Side Rendering)
Generating a page's HTML on the server for each request, rather than in the browser.
JWT (JSON Web Token)
A signed (and here, also encrypted) piece of data that proves who a user is, without the server needing to store session state.
CSRF (Cross-Site Request Forgery)
An attack where a malicious site tricks a logged-in user's browser into submitting a request to your app. Auth.js defends against this with a CSRF token that must be included in login requests — which is why the raw curl tests in this project had to fetch a token first.
Middleware / Proxy
Code that runs before a request reaches its actual page/route handler — used here for centralized access control.
Route group
A folder in parentheses, e.g. (protected), that organizes routes/layouts without adding a URL segment.
Hydration
The process of React "waking up" server-rendered HTML in the browser and attaching interactivity to it.
Connection pool
A reused set of open database connections, instead of opening/closing a new one per request — much more efficient. See lib/db.js.

14. What to learn next

In roughly the order it'll pay off:

  1. Plain React fundamentals, if not already solid — components, props, hooks, controlled forms.
  2. The Next.js App Router docs directly, especially Server vs. Client Components and data fetching.
  3. Basic SQL — SELECT/INSERT/UPDATE, primary keys, unique constraints — enough to read db/schema.sql and scripts/seed.js comfortably.
  4. How JWTs actually work under the hood (header/payload/signature) — worth understanding once, since it explains a lot of "why can't I just edit the session" questions later.
  5. Git branching workflows, once working with a team — this project so far has been single-branch, which won't scale to multiple developers.
